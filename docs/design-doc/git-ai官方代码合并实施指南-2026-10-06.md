## 1. 目标与硬性原则

本文用于指导公司 fork 合并官方后续代码。目标是吸收官方 bug 修复和可迁移的新功能，同时保持公司 fork 已经验证过的归因、上传、安装和看板行为。

### 1.1 Bug 合并原则

同一 bug 同时由公司和官方修复时，按以下顺序处理：

1. 先确认两边是否真的是同一根因，不能只根据提交标题或现象判断。
2. 根因相同且官方实现有对应回归测试时，以官方实现为主。
3. 官方实现合入后，保留公司特有的业务约束、日志字段、后端兼容、安装链和归因保护逻辑。
4. 如果官方实现会削弱公司已有证据链，则采用“官方核心修复 + 公司保护逻辑”的组合实现，而不是覆盖公司代码。
5. 合并后必须用原问题的复现步骤证明 bug 不再出现；只有编译通过不能视为合并成功。

### 1.2 归因审计原则

`unknown` 表示当前没有足够的可审计证据，不能为了降低 unknown 数量而强行改成 AI 或人工。

合并归因代码时必须遵守：

- 优先修复 checkpoint、hook、working-log、note 生成和 stats 链路中丢失证据的位置。
- 已有 AI attestation 和已确认的 `h_*` 人工 attestation 不得被恢复逻辑覆盖。
- 只有同时满足仓库、文件、时间窗口、session/工具证据的官方 recovery 才能选择性吸收。
- 官方“剩余 unknown 自动归为 KnownHuman”的兜底逻辑默认不启用；除非公司明确批准新的审计口径。
- 没有 authorship note 的提交继续按 `hasAuthorshipNote=false` 和 unknown 口径上传，不伪造 note。

### 1.3 新功能合并原则

官方新增功能按“可隔离、可验证、不会改变现有默认行为”优先迁移。以下五类本轮明确不迁移：

- Lite mode
- Token Usage
- Metrics reingest
- 官方 HTTP notes 默认行为及其完整实现
- WSL/MSI 默认安装链

其中 HTTP notes、WSL/MSI 不是永久禁止研究，而是保留公司现有实现和默认行为，不进行官方整批替换。后续如有单独需求，必须另立迁移方案。

## 4. 同一 bug 的合并流程

每个 bug 都必须建立一条“现象 -> 证据 -> 根因 -> 修复 -> 回归”的记录，不能只记录最终 diff。

### 4.1 定位与判定

对公司和官方提交分别记录：

- commit SHA、修改文件、测试文件；
- 触发条件和受影响版本；
- 丢失或误判的证据是什么；
- 是否改变 AI/Human/Unknown 优先级；
- 是否修改上传 payload、notes backend 或 daemon 状态机。

只有当根因和行为边界都一致，才认定为“同一 bug”。

### 4.2 合并顺序

1. 先迁移官方核心算法或 parser 修复。
2. 将公司特有的保护条件、诊断字段、后端字段和路径兼容补回。
3. 把官方回归测试改造成公司现有测试框架中的同形测试。
4. 运行原公司回归测试，再运行官方新增测试。
5. 用现场复现脚本验证原 bug 不再出现。
6. 检查 note、stats、upload payload 和 daemon 日志，确认没有从“unknown”误变为错误的 AI/Human。

### 4.3 冲突处理规则

- `src/daemon/checkpoint.rs`、`src/authorship/post_commit.rs` 冲突时，优先保护公司现有归因优先级和 archive recovery。
- `src/authorship/stats.rs` 冲突时，统一 commit 总数、逐文件 stats 和 upload payload 的行数口径。
- `src/integration/upload_stats.rs` 冲突时，优先保证公司后端必填字段、metadata-only 和幂等逻辑。
- `src/metrics/db.rs` 冲突时，不得直接用官方 schema 覆盖公司 schema；必须单独设计 migration。
- `src/config.rs` 冲突时，官方新增默认值不能无条件改变公司当前默认行为。
- `install.ps1`、`install_hooks.rs` 冲突时，保留公司 binary 来源、launcher、hooksPath、daemon 重启和升级探活。

## 5. unknown 恢复专项合并规则

### 5.1 公司实现作为主线

公司已有修复优先覆盖以下现场：

- Copilot `dirtyFiles`/`dirty_files` 路径兜底；
- AI checkpoint 位于旧 base 或 `old-*` working-log；
- archived AI state 与 line attribution 重建；
- `KnownHuman` 保存事件不能重新占有 AI 行；
- partial commit 后未提交 AI 文件继承；
- 非 UTF-8 文本文件路径和内容处理；
- 纯格式化/纯空白新增行不进入 unknown；
- 明确 legacy Human checkpoint 生成 `h_*` 人工 attestation。

### 5.2 官方 recovery 的可迁移部分

官方 session/time/commit metadata recovery 只有在以下条件全部满足时才允许迁移：

- 目标 commit 的仓库与候选 session 仓库一致；
- 文件路径与提交新增行有交集；
- 时间差在明确窗口内；
- metrics/session 中存在明确的 AI 工具和 session；
- 不覆盖已有 AI 或人工 attestation；
- recovery 结果写入诊断和 recovery metric。

官方的“没有 AI session 时将剩余 unknown 归为 KnownHuman”不作为默认迁移内容。metrics DB 不可用时必须保留 unknown，不能把数据库故障当成没有 AI 证据。

### 5.3 unknown 回归测试最低集合

- AI checkpoint 正常落 note，unknown 为 0；
- checkpoint 位于 archived/旧 base 时恢复 AI；
- partial commit 后下一提交继承未提交 AI；
- AI 后立即发生 KnownHuman 保存，不夺回 AI 行；
- 只有人工证据时生成 `h_*`，没有证据时保留 unknown；
- 有 AI 与无证据混合时，只恢复可证明的 AI 行；
- metrics DB 锁住或损坏时不发生人工误归因；
- 非 UTF-8 文件和中文路径仍能正确统计；
- 纯格式化改动不扩大 unknown 分母；
- deletion-only、rename、rebase、amend、cherry-pick 不丢失已有归因。

## 6. 明确不迁移的五类功能

### 6.1 Lite mode

Lite mode 会减少 rewrite 时的 commit graph 和 authorship note 处理，可能导致 replacement commit 缺少归因证据。公司当前目标是归因完整性和降低 unknown，因此本轮不迁移其 feature flag、daemon 分支和 ref transition 逻辑。

### 6.2 Token Usage

Token Usage 会新增 token parser、独立 DB、metrics event 和 daemon worker。它与公司 metrics event、SQLite schema、daemon 生命周期和看板字段存在基础设施冲突。本轮不迁移，避免引入与归因无关的资源和上传风险。

### 6.3 Metrics reingest

Metrics reingest 是历史指标重放，不会重新计算 authorship。官方实现依赖不同的 metrics schema、daemon control API 和 telemetry worker。本轮不迁移，避免重复上传、SQLite 锁竞争和公司后端幂等问题。

### 6.4 官方 HTTP notes 与 WSL/MSI 默认安装

公司已经有 HTTP notes backend、notes-db、Git notes fallback 以及定制安装/升级链。本轮不使用官方整批替换，也不采用官方 API key 默认切 HTTP notes 或 MSI 默认安装 WSL 的行为。后续如要迁移，只能按独立设计文档逐项适配。

## 8. 官方新增功能的迁移优先级

除上述明确排除项外，按以下顺序迁移：

### P0：直接影响归因正确性的修复

- agent hook payload 解析和文件路径提取；

- transcript/session 读取鲁棒性；
- diagnostics、错误边界和失败重试；
- 兼容更多 AI 工具但不改变既有工具优先级。

### P2：独立 CLI、配置和开发体验

- 不改变默认行为的配置项；
- help、diagnostics、版本和测试工具；
- 文档、示例和测试基础设施。

每个 P0/P1 功能必须先在公司分支建立功能清单和冲突文件清单，再合并代码。
